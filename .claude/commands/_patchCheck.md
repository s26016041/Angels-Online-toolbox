# _patchCheck（改版體檢）— 遊戲更新後，自動找出哪裡壞了並修好

天使之戀官方改版之後跑這一支。使用者不必再解釋一次背景，照下面做。

## ★★★ 常設授權（使用者 2026-08-27 明令）

> 「我授權給你開遊戲測試隨便測，如果需要的話。**不要每次都有東西沒修到。**」

所以跑這一支的時候：

* **不必再問可不可以開遊戲、可不可以動角色。** 需要幾台就開幾台
  （`app/game/login.py` 的 `launch` → `sign_in` → `pick_channel` →
  等 `character()` → `enter_game`；帳密在 `config` 的 `accounts`，
  `config.deobfuscate()` 解）。⑤ 層的打怪／走位、送同步請求、組隊解散
  這類**可回復**的動作直接做。
* ⛔ 授權**不包含會消耗東西或丟角色的**：真的買／賣／兌換／領獎／分解、
  換頻道、趴趴GO。那些照舊只驗「送得出去」，要真跑得另外問。
* **測完要收拾乾淨**：走位走回原點、組隊要解散、臨時 patch 要還原、
  臨時測試鈕要拆（[[test-via-button]]）。

### ⚠⚠⚠ 「不要每次都有東西沒修到」＝ 這三條是硬規則

1. **`–（驗不了）` 一律要追到底，不准當通過。** 每一項驗不了都要想辦法
   讓它變成 ✔ 或 ✘：
   · 晶化欄位驗不了 → **送一發 `0x3F` 同步**（零副作用）再驗
   · 目標欄位驗不了 → 跑 `action_check --yes`（寫入讀回才是決定性證據）
   · 隊員陣列驗不了 → **真的組一次隊**再解散（⚠ 兩台要在**同一個分流**，
     跨分流邀請送得出去但對方永遠收不到 —— 2026-08-27 實測）
   · 經驗球分類／裝備品質驗不了 → 背包裡本來就沒那種東西，記錄原因即可
2. **收尾前把五層的結果逐項列出來**（✔／✘／–＋每個 – 的處置），
   不准只講「全綠」。上次就是這樣漏掉晶能的。
3. **沒有 AOB 的偏移要主動重驗**（見第 5 步的必驗清單），
   尤其 `entity.VT_STATE` 只要是「沒中」而不是「位移」。

### ⛔⛔⛔ 介面訊息裡的 `py tools\xxx.py` **要留著**（2026-08-27 犯過一次）

我看到「資料表過期」警示叫使用者去跑 `py tools\recheck_tables.py`，就自作主張
把 `app/` 底下六處含開發指令的訊息全改成「跟 Claude 說一聲」。**當場被打回：**

> 「我不是說不可以出現，**我要出現**，不然我很難處理 BUG。
>  是我在使用指令的時候為何你沒有自己去做這些事情？
>  patchCheck 這不是他份內該做的嗎」

所以：

* ✔ **介面訊息裡的工具名／指令／原始碼路徑一律保留** —— 那是**使用者自己
  抓 bug 用的診斷資訊**，拿掉反而害他。⛔ 不准以「不該露給使用者」為由清掉。
* ⛔ 但那**不是丟給他的待辦事項**。他下 `/_patchCheck` 的時候，那些事
  **本來就該我自己做完**（見第 7 步的「④ 層不准留著警示收尾」）。
* ★★ **教訓：聽到「不該露這個」，先問清楚是「不該顯示」還是「不該由我來做」。**
  我直接跳到前者，改了六個檔才發現搞錯，還得整包 revert。
  **拿不準使用者在講哪一件事就問一句，不要動手改一整批檔案。**

## 五層，全綠才算過

| 層 | 工具 | 驗什麼 | 要不要進遊戲 |
|---|---|---|---|
| ① 位址 | `patch_doctor.py` | 特徵唯一性、模擬改版、名字交叉驗證、寫死位址稽核 | 掃特徵登入畫面就夠；它附帶的執行時體檢要進遊戲 |
| ② 偏移 | **`verify_offsets.py`**＋`patch_doctor.py`（`kind="off"` 那幾段） | 物件版面有沒有搬家 | 要 |
| ③ 讀取 | **`tab_check.py`** | **逐分頁**驗它實際會讀的每樣東西 | 要 |
| ④ 查表 | **`recheck_tables.py`** | 寫死表 vs 記憶體；順便回答 setting 要不要重解包 | 要 |
| ⑤ 動作 | **`action_check.py --yes`** | 真的打一隻怪／走一步 | 要，且有副作用 |

⚠⚠ **①②③④ 全綠 ≠ 功能正常。** 2026-08-11 那次 selfcheck 13/13 全綠、位址
全綠，掛機還是完全廢的 —— 因為真兇是「`usequickkey` 第三個參數從 0 變成 1」
（呼叫慣例的**語意**變了，靜態工具永遠看不到）。所以最後一定要**實際打一隻怪**
確認，或請使用者掛五分鐘回報。

### ⚠⚠⚠ 綠燈也可能是假的 —— 2026-08-25 的教訓

那次①②③④全綠、還發了版，結果**晶能是壞的**（`energy.OFF_ENERGY` 已經
0x54 → 0x34），是使用者自己發現的。兩個原因，都已經修掉，但要知道為什麼：

1. **「沒同步 = 全 0」會通過驗證。** 晶化資料要開過晶能視窗（送 `0x3F`）才有；
   沒同步時整片是 0，而 0 通過每一道逐欄驗證 → ②③都印綠燈。
   現在改成「四欄全 0 → 判**驗不了**」。看到那行就去開一次晶能視窗再跑。
   ★ 通則：**任何「要先送請求才有資料」的欄位，全 0 一律當沒驗到**
   （memory `lazy-sync-request-first`）。
2. **②層以前「要每一台都失敗才算壞」。** 5 台有 2 台讀到的垃圾剛好像合理值
   → 整項印綠燈。現在改成**只要有任何一台「驗得了而且驗不過」就是壞**；
   驗不了（NA）不參與判定。

**所以看報告時：`–（驗不了）`跟 `✘` 一樣要追**，別當成通過。
`tab_check` 現在也會把驗不了的項目印出來（以前它靜靜消失）。

## 0. 先確認真的改版了

```
Get-Item "D:\AngelsOnline\Angels Online Global\angel.dat" | Select LastWriteTime
Get-Content "D:\AngelsOnline\Angels Online Global\patch.log" -Tail 6
```

⚠ `patch.log` 寫 `no update needed` **不能當作沒改版** —— 要看 angel.dat 的檔案時間。
⚠ 順便看 `UPDATE.PAK` 的時間：它也變了 → 從資源包抄來的寫死表要重新核對（見第 6 步）。

## 1. 跑體檢

遊戲開著（登入畫面就夠）：

```
$env:PYTHONUTF8=1; py tools\patch_doctor.py --dump
```

`--dump` 會把映像存到 `reports/angel_image.bin`，**之後遊戲關了也能離線查**
（`--image reports\angel_image.bin`）。這很重要：診斷常常要來回好幾趟，
不要每次都叫使用者開遊戲。

主控台只印結論；全量在 `reports/patch_doctor.txt`，可貼的修法在
`reports/patch_doctor_fix.md`。

## 2. 讀懂它的四種判定

| 判定 | 意思 | 要做什麼 |
|---|---|---|
| **位移** | 特徵自己跟上了，值變了 | **正常，不用管**。改版當天大部分都長這樣 |
| **壞：沒中** | 函式被重新編譯／程式碼改寫 | 看 fix 檔的「最接近」候選＋反組譯，套新 pattern |
| **壞：模糊** | 特徵不夠獨特，撞到別人 | **先挑對是哪一個**（見下），再照建議往後延伸 |
| **⚠ 只有『只遮目標』那層唯一** | 還沒壞，但**下次改版一定壞** | 順手修掉，fix 檔有現成建議 |

★ 「模糊」最危險：`data` 類會**安靜地保留舊值**，症狀離現場很遠
（2026-08-11 就是這樣 → 自動登入卡在「等遊戲開好」）。

## 3. 「模糊」要怎麼挑對候選

報告裡每個候選都附反組譯。判斷順序：

1. **字串內容**當錨（最強）—— 附近有 `push "某字串"` 就用 `str_at`/`str_val`。
   怪物表 vs 寵物表（`Npc`/`Pet`）、技能表（`Magic`）、`lua.CTX_PTR`
   （`UpdateEquipPetNew`）都是這樣分的。字串位址會移，**內容不會**。
2. **名字定位**（Lua 綁定表）—— 體檢報告的「名字定位交叉驗證」那一段。
   遊戲的 Lua 綁定表是 `{名字, 函式}` 成對，SIGS 裡的 fn 有幾支查得到
   （2026-08-25 是 7 支）。數字會變，以報告印的為準。
3. **指令骨架**往後延伸 —— fix 檔會算好「多蓋幾 bytes 才唯一」。
   ⚠ 別延伸到跨過 `ret` 進到下一支函式（那不穩）。

⛔ **絕對不要**把要解出來的位址留在特徵裡當錨（tautology）——
那等於拿答案比對答案，`.data` 一位移就整段失敗。這條是硬規則。

## 4. 套用 → 驗證（一定要做完）

改 `app/game/locate.py` 的 SIGS。**如果新特徵的 pattern 位元組是照現在的映像
重抄的，`known` 也要一起改成現在的值**（`_auto_mask` 靠 `known` 認出「哪個
4-byte 視窗是目標」，兩者必須一致）。同一個模組裡寫死的那份退路常數
（例如 `lua.CTX_PTR = 0x...`）也一起更新。

```
py tools\patch_doctor.py --image reports\angel_image.bin   # 應該 0 壞
py tools\verify_sigs.py                                    # 遊戲開著；唯一性＋模擬改版
```

## 5. 結構偏移（版面）壞掉的話　★ 這一層最會咬人

症狀是特徵好好的、功能卻不對。這類**不是位址位移**，是官方在物件裡加減成員，
而且**壞了完全沒有錯誤訊息**：舊偏移照樣讀得到（讀到別的成員）、照樣寫得進去。

```
py tools\verify_offsets.py        # 進遊戲後跑；每個偏移用不變量驗一次
```

⚠ 掛機開著跑最好 —— 「目標欄位」那一項要有選定目標才驗得到（沒有就顯示 `–`）。

⛔ **別把「目標 ID 不在實體清單裡」改回判失敗**（2026-08-27 已修，說明留在
`verify_offsets.py` 的註解裡）：目標怪被回收之後**遊戲不會清掉那個欄位**，
留著一個死掉的 eid 完全正常。當時就是這樣誤報成「偏移搬家」，而同一時間
`action_check` 寫入讀回＋怪血真的掉，證明偏移好得很。
純讀分不出「舊目標」與「讀錯欄位」→ 只在**血量欄不在 0~100**（正面證據是垃圾）
時才判 ✘，其餘回 `–` 並用 ⑤ 層的寫入讀回當決定性證據。
★ 通則：**亂喊狼來了跟漏抓一樣糟** —— 會訓練人忽略紅燈。沒把握就回「驗不了」。

2026-08-11 那次**同一個物件裡不同成員的位移量不一樣**，不能用同一個 delta 推：

| 偏移 | 舊 → 新 | 位移 |
|---|---|---|
| `quickbar.TABLE_OFF` | 0x609C → 0x603C | −0x60 |
| `player.VT_OFF_FROM_MGR` | 0xCB68 → 0xCB08 | −0x60 |
| `robot.ROBOT_READY_OFF` | 0xF35C → 0xF2FC | −0x60 |
| `team.MEMBERS_OFF` | 0x31A0 → 0x3140 | −0x60 |
| `team.PENDING_OFF` | 0x338C → 0x332C | −0x60 |
| **`entity.OFF_TARGET`** | 0x2D8 → **0x270** | **−0x68** |
| **`energy.OFF_ENERGY`** | 0xB8 → **0x54** | **−0x64** |

2026-08-25 又證明一次（同一個物件、不同成員位移量還是不一樣）：

| 偏移 | 舊 → 新 | 位移 |
|---|---|---|
| **`energy.OFF_ENERGY`** | 0x54 → **0x34** | **−0x20** |
| `entity.VT_STATE`（vtable，不是偏移） | 0x7E3DD8 → 0x7E5E10 | +0x2038 |
| `player.VTABLE_RVA`（同一支建構函式裡） | 0x7E3DF4 → 0x7E5DDC | +0x1FE8 |

⛔ 所以**不准拿別的欄位的位移量去推**，一個一個驗。

### ★★★ 這幾個偏移**不會自動跟上**，改版後一定要手動重驗

②層的自動部分只涵蓋 `locate.SIGS` 裡 `kind="off"` 那 15 段。實際上
`app/game` 有 **93 個偏移常數**，其餘的全靠「讀取端驗證」擋 —— 而驗證擋得住
大部分、擋不住全部（2026-08-25 晶化就是 5 台有 2 台矇混過關）。

**最該盯的是這一組**（文件自己都承認沒有錨可掛）：

* **`energy.OFF_ENERGY`（＋它 +4/+8/+12 那三欄）** —— 晶化介面整個是 Lua 寫的，
  C++ 那邊沒有穩定的指令骨架。**已經連續兩次改版都搬家**（8/11、8/25）。
  ⚠ 特別注意：**只要 `entity.VT_STATE` 那段特徵沒中，就代表狀態物件開頭被
  重排了 —— 這一組幾乎一定跟著搬**，8/25 就是這樣。

  重定位方法（唯一有效的一招）：
  1. 開著遊戲，記下狀態物件前 0x800 bytes
  2. 送一發同步請求 `0x3F`（`energy.sync(mv)`，純要資料、零副作用）
  3. 再記一次，**diff 出哪些格子變了**
  4. 跨五台交叉比對語意：**−1 哨兵值＝「抽到的屬性」（最硬的錨）**、
     固定 10 ＝每次點數、因人而異的＝能量、後面 12 格＝各屬性累積點數
  5. 起點 = 「抽到的屬性」那一格 −4

* 其餘沒有 AOB 的偏移清單：跑 `py tools\coverage_audit.py` 看，或直接
  AST 掃 `app/game/*.py` 的 `OFF_*` 常數比對 `locate.SIGS`。

做法：找一處遊戲自己用那個偏移的程式碼，把 disp32 讀回來 →

```
py tools\find_off.py 0x31A0            # 誰在用這個偏移
py tools\find_off.py --at 0x58c70d 0x1a   # 把那一段直接印成 pattern 位元組
```

★ 找不到使用點（像 `team.MEMBERS_OFF` 舊值）本身就是強烈訊號：**它已經搬家了**。
★ 純 Lua 的介面（晶化那組）C++ 沒有錨可掛 → 改用「送一發同步請求，看**哪一格
會變**」定位，再跨五台交叉比對語意（−1 哨兵值、固定 10、因人而異的值）。
★ 定完一律加進 `locate.SIGS`（`kind="off"`）讓它下次自動跟上。
⚠ `off` 類的目標值不在模組範圍內 → `_auto_mask` 不會自動遮，**pattern 裡要
自己寫 `??`**，不然又是拿答案當錨。

## 6. 進遊戲驗「每個分頁都讀得對」（③ 讀取層）

位址對了不代表**版面**對了，更不代表分頁讀得到它要的東西。登入一台再跑：

```
py tools\tab_check.py        # 逐分頁；有幾台就驗幾台
py tools\selfcheck.py        # 13 項共用底層（tab_check 已涵蓋大半，快就順手跑）
```

`tab_check` 的對照表是用 AST 掃 `app/tabs/*_tab.py` 的相依關係列出來的
（分頁 → 它呼叫哪些讀取函式），不是憑印象寫的。目前涵蓋：

* **收益監控**：角色屬性（等級/HP/MP/經驗/金幣合理性）、經驗球分類
* **自動掛機**：座標、場景、地形圖、周圍怪＋範本表交叉比對、**目標欄位**、
  快捷欄 4 頁、技能範本＋射程表、SP、背包／金幣、身上裝備耐久、精靈設定樹、
  補給判斷、分流／伺服器名
* **自動登入**：伺服器清單、角色清單
* **分身總控**：隊伍成員、趴趴GO 表
* **能量晶化**：晶能欄位、可分解清單
* **販賣裝備**：裝備品質／耐久

⚠ 每一項都要有**能分辨對錯的證據**（範圍檢查或兩個來源交叉比對），
不是「有回值就算過」。加新檢查時照這個標準。
⚠⚠ 跨來源比對的值**一定要當場重讀**：`sp_now` 是拿「子物件的 MP 等不等於
角色屬性那份 MP」認基準的，用幾秒前的快照會因為 MP 自然回復而假失敗
（實際踩到，五台裡一台紅燈）。量測工具自己把數據弄假是老坑。

需要實際登入時：帳密在設定檔（`app.config.config` 的 `accounts`，
`config.deobfuscate()` 解），流程照 `app/game/login.py`
（`sign_in` → `pick_channel` → 等 `character()` → `enter_game`）。
★ 開遊戲／登入／動角色**已經有常設授權**（見檔頭），不必再問；
⛔ 但會消耗東西或把角色丟走的動作仍然要另外問。
⚠⚠ 任何碰遊戲記憶體的腳本，**第一件事是 `locate.warm(sc)`** ——
沒 warm 就寫全域＝拿舊位址砸新版遊戲（見 memory `patch-doctor-command`）。

## 7. 查表正確 ＋ setting 要不要重新解包（④ 查表層）

**先別急著叫使用者重新解包。** `UPDATE.PAK` 換了不代表表變了；使用者的實務
經驗是**「通常只有大更新新增內容才要重做」**，而那句話現在可以**驗證**：

```
py tools\recheck_tables.py        # 要進遊戲，最後會直接給結論
```

它自己會印「setting 這次要／不必重新解包」。對帳項目：

| 項目 | 過期後果 | 對帳來源 |
|---|---|---|
| `skill_range.tsv.gz` | ⛔ 走位停太遠 → 零傷害，不報錯 | Magic 範本 +0x50/+0x54 |
| `jumpmap.tsv` | ⛔ 傳到錯的地方 | JumpMap 範本 +0x04 場景/+0x10 X/+0x14 Y |
| Item 表 ↔ 背包 | 驗表指標＋物品的種類 ID 欄位 | 每件物品都要查得到範本 |
| Npc 表 | 王／等級／滿血的來源 | 抽樣合理性＋場上的怪查得到 |
| 物品名稱 | 只影響顯示（查不到 → 顯示編號） | 只報涵蓋率，**不擋** |
| 道具圖示 `item_icons.zip` | 只影響顯示（查不到 → 沒有圖示） | 只報涵蓋率，**不擋** |

* **全對** → 不必解包。`py tools\stamp_tables.py` 蓋章，掛機頁警示就熄。
* **對不上** → 先看下面那招能不能自己補；真的補不了才請使用者重新解包
  （`D:\RPGViewer` 是 GUI，我們代跑不了），然後
  `build_item_names / build_jumpmap / build_skills / build_skill_names /
  build_skill_range / build_item_icons` 重跑一輪再蓋章。

### ⚠ 官方改版**新增道具**時要重跑 `build_item_icons.py`

`GAMEDATA\shape\item\*.SHP` 解出來打包的。新道具的圖不在包裡 → 強化裝備分頁
那格會是空白（安全退化，不會做錯事），但看起來就像壞了。

★ 圖示編號是從記憶體讀的（範本 `+0x00`），編號那半改版自動跟上，
  只有「編號 → 圖檔」這半要重跑。涵蓋率由 `recheck_tables.py` 直接報。

## 8. ⑤ 動作層 —— 靜態工具的極限，一定要補這一刀

①~④ 全綠**還是可能整個功能是廢的**。2026-08-11 的實錄：位址全綠、
selfcheck 13/13、資料表全對，但掛機站在怪旁邊完全不出手 —— 真兇是
`usequickkey` 第三個參數從「0 可以」變成「0 一律失敗」。
**參數個數沒變、函式頭沒變、特徵完美命中**，只有真的打一隻怪才驗得出來。

**已經有工具了**（2026-08-25 補的；會動到角色，但**常設授權涵蓋**，見檔頭）：

```
py tools\action_check.py --yes            # 打怪＋走位，每一台都驗
py tools\action_check.py --yes --walk     # 只驗走位（副作用最小）
```

它做的就是最小可信實驗：設目標 → 叫快捷鍵 → 看怪血% 有沒有掉／MP 有沒有扣；
走位則是 `walk_exact` 走三格再走回原點。判定：
`✔` 有硬證據／`✘` 叫得出去卻沒反應（**這就是改版壞掉的樣子**）／`–` 沒驗到。

⚠⚠ **要自己寫探針的話，這四個坑先看過**（2026-08-25 我全踩了一輪，
每一個都會讓你誤判成「改版把功能弄壞了」）：

1. **一定要用 `entity.set_target()`（目標 ID ＋ 血量欄兩欄一起寫）**，
   ⛔ 不是 `set_target_id()`。只寫 ID 的話血量欄停在 0，遊戲會認定目標已死
   而**直接跳過攻擊** —— 症狀是「叫了 8 下、指令槽 8 次全成功、怪血一動也不動」。
2. **測試對象一定要選「射程真的夠得到」的怪**：打不到本來就不會掉血也不會扣
   MP，判成 ✘ 就是誤報。配不出來寧可回「沒驗到」。
3. **走位要排在打怪之前，而且先清掉目標**：打完怪角色還在交戰狀態，遊戲自己
   的「接近怪」狀態機會蓋掉我們送的目的地，座標一格都不動。
4. **角色可能正被別的功能佔著**：自動練技會讓角色一直原地施法
   （動畫狀態 `'Cast'`），走位指令當然沒人理 —— 那是驗不了，不是壞掉。
   另外 `walk_exact` **不尋路**，終點要用 `grid.clear_line()` 確認直線走得過去。

其他功能的最低驗證（⛔ 下表**不在**常設授權裡的那幾項，要真跑得另外問）：

| 功能 | 硬證據 |
|---|---|
| 走位 | `WALK_FN` 後座標真的變 |
| 自動登入 | 登入畫面 → 進遊戲，視窗標題出現帳號 |
| 換頻道／趴趴GO | 標題分流變／場景編號變（**會把角色丟走**） |
| 賣裝備／兌換／領獎／分解 | 只能驗「送得出去、遊戲有反應」，**別真的跑**（會消耗東西） |

★ 最省事也最可靠的一招：位址層修好之後**請使用者自己掛五分鐘**回報。
他的回報（「站著不動」「不出手」）比任何自動檢查都準。
